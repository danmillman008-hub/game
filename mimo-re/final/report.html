1. What Mimo is, mechanically

Mimo is a content-driven mobile learning client for a server-authored curriculum. The app itself contains almost no course design: it ships 19 learning paths, 1,029 tutorials, 1,947 chapters and 18,272 lesson slots per language pack, all as JSON + an XML-like lesson markup language, and renders them with a small number of specialised lesson engines (interactive markup player, executable-code player, quiz/selection player). Everything that looks like "curriculum intelligence" — which lesson comes next, whether an answer is right, how many keys you have left, which experiment you are in — is decided by a mix of client rules and server responses, and this report separates the two in every case.

3. The five engines, in one line each

  1. Curriculum engine — manifest of paths → sections → tutorial IDs (startIndex/endIndex per section, verified consistent in all 19 paths), tutorial files loaded lazily from the language pack, chapters typed practiceLevel1..3 / challengeLevel0..2.
  2. Lesson DSL engine — markup parsed into modules (<p>, <code>, <interaction>, <selection>, <output>, <database>), each module carrying a visibility rule and, for assessed modules, an answer model.
  3. Validation/execution engine — two grading paths: local offset matching for interactive lessons, remote file execution for executable lessons with per-test feedback.
  4. Progression/economy engine — sparks → daily goal → coins → store; keys gate lessons; streak/challenge/league/leaderboard drive retention; all server-authoritative with local optimistic projection.
  5. Content operations engine — publish sets + language packs + DeveloperMenu live preview over Pusher, with experiments able to swap a whole track for a variant.

4. Architecture in one paragraph

Orbit-MVI + Redux-Kotlin over a Room cache, with Retrofit/kotlinx.serialization transport, WorkManager for deferred progress sync, a Jetpack-Compose layer that coexists with 809 XML layouts and 55 Activities, Firebase (Auth, Messaging, Remote Config, In-App Messaging), RevenueCat for entitlements, Adjust + Mixpanel for attribution/analytics, Customer.io for lifecycle messaging, Glance for the streak widget, and Rive for the streak/chapter-end animations. The app is a thin, heavily instrumented client for a fat content-and-economy backend; that single sentence is the most important architectural fact for anyone porting it.

5. What transfers to a Konkur (Iranian university-entrance) product

Transfer is not about copying screens. Three mechanisms carry most of the value:

  • The lesson DSL + offset validation (Mode A: direct learning) — because it makes authoring cheap and grading exact without a code sandbox.
  • The curriculum/publish-set model (all three modes) — because an exam product lives or dies on content versioning and on being able to re-plan a study path mid-course.
  • The economy-with-server-authority pattern (gamification across A/B/C) — because Iranian users are extremely price- and value-sensitive; keys/coins/streak translate well, while leagues and social features need different framing for the Konkur audience.

Section 19 gives the full 40-row transfer matrix with Reuse / Adapt / Exclude verdicts. Items to exclude outright: the AI tutor's free-text chat in its current form (cost + moderation + Persian quality risk), the entire paid-store/RevenueCat subtree (no IAP channel), Adjust/Facebook attribution (blocked/unusable), and the code-execution engine (Konkur is not a programming exam).

3. Semantics

3.1 Flattening (the core operation)

The editor renders a flattened code string: flat = concat(value of each <text> in document order, mapping <text type="break"/> → "\n"), with XML entities decoded (&lt; → <, etc.). Offsets index into flat, 0-based, [startIndex, endIndex) half-open. Cross-check: 17,526 / 17,526 gap options are in bounds under exactly this rule, and no alternative rule (ignoring breaks, 1-based, per-line) is consistent with all of them.

3.2 Answer model

Interaction Where the correct answer lives Evidence
fillTheGap The code slice at each gap_option range, i.e. flat[start:end]. Decoy chips carry correct="false"; no correct="true" exists anywhere in the corpus ⇒ correct chips are derived from the code, decoys are authored. V counts + I derivation
validatedInput The slice at flat[start:end] (e.g. an identifier or literal the learner must type). startIndex/endIndex sit on the <interaction> itself. V
selection <item correct="true"> — exactly one per block (0 blocks with none, 0 with two) V
output Expected console text for the code block, shown as expected output, not compared to an interaction V (presence) / I (use)

The derived-answer rule is the elegant part of the design: the author never types the answer twice. Writing the correct code is authoring the answer; only distractors are extra work. This is why the corpus can afford 13k assessed blocks with 1,649/1,535/1,669 blocks of 1/2/3 gaps respectively (distribution 1→1,649, 2→1,535, 3→1,669, 4→930, 5→419, 6→203, 7→56, 8→28, 9→7, 10→3, 11→2, 12→3).

3.3 Visibility state machine

visible-if ∈ {always, wrong, correct} — 12,171 / 13,043 / 143 occurrences. Per assessed module: unanswered → checked(wrong|correct). Modules with visible-if="wrong" are remedial feedback (13,043 of them, 91.5% of interactive lessons have at least one); visible-if="correct" is rare (143) and used for escalation ("you got it — here's the deeper explanation"). Recovery: the learner can re-check, and after repeated failure the app offers see_solution / hints (interaction_hint_*, V strings).

3.4 Multi-block lessons

A lesson is a document, not a single exercise: 58,806 <code> blocks over 14,248 lessons (≈4.1 per lesson), each with its own name (filename) and codelang (11 languages), and each independently assessed or purely demonstrative. Ordering is document order; there is no explicit sequencing attribute.

  • <database bootstrapScript="…"> (574 in 269 SQL lessons…): declarative table + row content seeded by a bootstrap SQL script, rendered as a result grid with <header>/<data> cells.

07 — Answer validation and code execution

Mimo grades with two independent engines and one shared contract: the client decides nothing about correctness in the executable path, and everything in the interactive path.

Part A — Interactive lessons (client-authoritative)

A1. Model

Each assessed block carries its own answer model inside the markup (§06). There is no separate answer key file, no separate answer network call, and no obfuscated answer database: the answers are the code. Consequently the client can grade offline, instantly, and without leaking anything beyond what the lesson already shows.

A2. Grading algorithm (V offsets, V grammar)

checkFillTheGap(block, placed):
    correct = true
    for i, gap in block.gaps:                  # gaps ordered by startIndex
        want = block.flat[gap.start : gap.end]
        got  = placed[i]                       # text the learner put there
        correct &= (normalise(got) == normalise(want))
    return correct

checkValidatedInput(block, typed):
    return normalise(typed) == normalise(block.flat[block.input.start : block.input.end])

checkSelection(block, tapped):
    return set(tapped) == {item.value for item in block.items if item.correct}

Evidence that this is the real rule (not a guess): * every one of the 17,526 authored ranges is in bounds of flatten(content) under the break→\n rule and no other candidate rule reproduces that in-bounds property; * the authoring model has no place to put the expected text except those ranges: <option> with a range has no content and no value attribute (17,526 occurrences, zero exceptions); * decoy chips are the only options with text, and they are all correct="false" (4,939/4,939) — i.e. the author writes distractors only.

B3. What the server does (I, strongly bounded)

  • It compiles/executes the submitted files and evaluates a test suite generated from the lesson's own solvedContent — the only per-lesson truth the client ships. The internal name appears in an error literal: Error when executing the MFEL. Error message: ⇒ an internal service ("Mimo File Execution Layer") owns execution.
  • It returns human-readable description per test, so the server authors the test prose; the client never contains the expected values of the checks.
  • It hosts the built artefact (hostedProjectUrl for lessons, hostedFilesUrl for playground) — for HTML/CSS/JS lessons the "result" is a URL opened in a WebView, not stdout.
  • It is the only path that can grade non-web languages (python/node/sql/swift): the client contains no interpreter for them.

B4. Client-side state machine (V literals + class names)

editing --run--> running --(tests_passed)--> passed --> storeProgress --> next module
                        --(tests_failed)--> failed --> show tests --> edit again
                        --(compiler_error)--> error --> show error toast/dialog

passed/failed --> see_solution? --> CodeSwitch(Solved|User) diff --> confirm dialog

Autosave is continuous (AutoSaveCodeService, savedFiles), so a lost run never loses code. Progress is written by executeLessonAndStoreProgress — only on a passing run (V method name) — which is why the whole offline story for executable lessons is "you cannot progress offline", whereas interactive lessons do progress offline (see §16).

B5. Security consequences (verified public facts only)

  • The submission endpoint accepts arbitrary user code and executes it server-side. Any implementation of this pattern is a remote-code-execution surface by construction; it must be sandboxed, CPU/memory/time limited, network-egress blocked, and rate limited per account. Mimo's client-side timeout (RunCodeEvent.timeout) shows the client expects long runs.
  • The preview variant executes unpublished content: it is an authoring tool reachable from the app. If it were reachable outside the dev flow it would expose pre-release course material. No exported component leads to the Developer Menu (V), so the exposure is limited to builds where the menu is unlocked by a flag/gesture (U which).
  • The client never holds expected outputs ⇒ a local attacker cannot mine answers from the APK for executable lessons, but can for interactive lessons (answers are the code itself). That asymmetry is inherent, not a bug.

Part C — Unified grading contract (the part to port)

C1. One interface, two implementations

C2. Attempt accounting

C3. Normalisation policy (must be decided, Mimo's is unknown)

For Persian Konkur content the checker needs an explicit, testable policy: trim, collapse internal whitespace, Arabic/Persian character folding (ي→ی, ك→ک), Persian and Arabic-Indic digit folding (۰-۹ / ٠-٩ → 0-9), ZWNJ handling (نیم‌فاصله), optional diacritic stripping, and number-format tolerance (٫ decimal separator vs .). 09 — Practice, difficulty and adaptive progression

Mimo has four separate difficulty mechanisms that are often confused in product discussions. This section separates them, because only two of them are actually adaptive.

# Mechanism Granularity Adaptive? Evidence

1. The practice hub

What it offers (V strings): real-life scenarios, review & reinforcement, problem-solving; filters on completion status, paths, content type; a "Hide completed" toggle; free-text search with a dedicated no-results state; plus practice_stats-driven figures.

What it actually is (V contract): practice content is re-served existing chapters, not a separate corpus. PracticeContentResponse(chapterId, trackId, tutorialId) carries only identifiers — the client then loads that chapter from the shipped pack. That is why the practice hub can cover 1,947 chapters instantly and why "practice" never grows the content size.

Statistics (V): PracticeStatsResponse(duration, chaptersCompleted) — two metrics only: time spent and chapters completed. No accuracy, no per-topic weakness, no difficulty rating.

Smart practice (V): SmartPracticeChargedModal, SmartPracticeMasteredModal — a consumption-gated flow (charged) that ends in a mastery claim. The selection logic is server-side (I); the only local input available to it is progress + practice statistics.

Offline (V): practice_offline_*; practice therefore needs the network for selection but not for rendering the chosen chapter (I).

2. Difficulties in detail

2.1 Chapter levels

Authored, not computed. Distribution shows a deliberate 3-tier skew: entry (practiceLevel1, 62% of lessons), mid (practiceLevel2, 13%), hard (practiceLevel3, 22%). Challenges exist at three levels but are only 2.4% of lessons. A level is a label on content, not a rating of the learner.

2.2 Hard mode

  • The authored variant is a parallel lesson body (hardModeContent), not a parameter.
  • Selection is per lesson and persists; 6,058 of 14,248 interactive lessons have a variant (42.5%). Copy proves intent: hard_mode_feature_intro_*, and the tutor variant (hard_mode_ai_tutor_intro_*) exists precisely because hard mode raises failure rate and the product wants support at that moment.
  • Gated by experiment_hardmode_v2_android (V remote-config key) ⇒ hard mode itself is an experiment surface.

2.3 Fast mode (the one true automatic adaptation)

Verbatim product copy (V): "Fast mode means fewer, harder exercises per chapter. You choose the mode" and "Fast mode gives you fewer, harder exercises per chapter"; entry point "You're breezing through!" with Turn on fast mode / Keep regular mode; exit point "You're back to regular difficulty." Mechanics (I, from copy + chapter model): the app watches completion pace; when a learner finishes a chapter unusually quickly it offers to skip the easier slots of future chapters, keeping the hardest ones. The filter is applied at chapter-assembly time, client-side, on lesson records already in memory — no new endpoint exists for it ⇒ the mode changes lesson selection, not content.

2.4 Pacing

ShowPacingDialog + pacingmechanic literals and TrackEtaResponse(currentPaceMinutesPerDay, sections[]) show a pace calculator: minutes/day ↔ projected completion date. Chapter end renders it (chapter_end_progress_eta_quarter_*, …_half_*, …_three_left_*) and the reactivation flow re-asks the goal (reactivation_set_goal_*) — i.e. the "adaptive" loop is mostly goal re-negotiation + schedule recomputation, not difficulty modelling.

  • No exam-date-aware scheduling: there is no deadline concept anywhere in the model.

4. The outbox pattern (V + I)

lesson_progress.in_queue + LessonProgressQueue + LessonProgressRepository$postUnsyncedLessonProgress$2 → DELETE FROM lesson_progress WHERE lesson_id IN (…) on success. So: 1. grading writes a row (or updates it) with in_queue=1; 2. a WorkManager job (WorkManager present, 19 services) posts unsynced rows to /v1/tutorials/{tutorialId}/progress; 3. on 2xx, the rows are deleted from Room, not marked synced — meaning Room holds only un-synced progress plus completion tables. That is why the app can be reinstalled without losing progress (it is on the server) but shows nothing offline until it syncs.

chapter_completions and tutorial_completions follow the same pattern with created_at / updated_at timestamps and no sync flag — their rows are the app's local read model of "what's done", refreshed from the server.

2. Sync design (V + I)

                 └─► POST /v1/tracks/{trackId}/completion (I)

Properties of this design worth noting: 1. Deletion on success means Room never accumulates history; the server is the only long-term record. No conflict resolution: progress is monotonic (tries, attempts, completed_at), so last-write-wins is safe by construction. That is a deliberate and clever simplification. 3. No content sync: the app never asks "is my curriculum current?" — version skew between a user's progress and a newer pack is resolved server-side by publishSetVersion (I). 4. Connectivity probe: /v1/health/connectivity provides an explicit online check for the offline views (offline_view_refresh), rather than relying on the OS network callback alone.

2. Mode-by-mode design consequences

Mode A — LearnHarness (direct learning)

Adopt the lesson DSL + offset grading + visible-if remediation almost unchanged. This is the cheapest high-fidelity part of Mimo to reproduce: the corpus proves the grammar is small (26 tags, 3 visibility values) and self-consistent. Required additions: <equation>, <figure>, RTL text markers, Persian normalisation, and per-option ۳-گزینه‌ای negative marking.

Mode A should be fully offline-capable (Konkur's network reality) — which Mimo already is for interactive lessons; only the executable path forces the network, and Konkur excludes that.

Mode B — EPM (exam centre)

Mimo has no exam mode: no timer, no per-question budget, no negative marking, no seating/section ordering, no post-exam analytics. Everything here is new work. Three Mimo mechanisms are still directly reusable: * progress triple / version algebra — an exam is pinned to a blueprint version; * attempt accounting (tries, attempts) — becomes per-question attempt history; * outbox sync — an exam taken offline must queue its result and hash.

The EPM must add what Mimo never had: timing, scoring policy, question-bank rotation, answer-key versioning, and integrity (signed bundles).

Mode C — Study-plan card path (مسیر کارت‌محور)

Mimo's closest analogue is the pacing/ETA + fast-mode + reactivation cluster, and it is insufficient: it has no deadline, no per-topic weakness and no session-length model. Build the card engine on three inputs Mimo does not collect: days_to_exam, per-topic accuracy with recency decay, available minutes/day. Reuse from Mimo: the card visual language (12dp cards, 8/12/16/24 spacing), the daily-goal ring, and the reactivation copy pattern when a day is missed.

Gamification across A/B/C

Mode Primary currency Secondary Avoid
A LearnHarness sparks/XP + streak keys-as-credits league (no cohort)
B EPM rank percentile + accuracy badges coins streak wager during exam week
C Plan cards completion of today's card streak XP inflation (dilutes signal)

Rule: one currency per mode, shared balance. Mimo's five-currency system works because its content is endless; Konkur's syllabus is finite, so currency inflation would be visible.
