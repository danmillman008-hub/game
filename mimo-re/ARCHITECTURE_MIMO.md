## ۳. زبان درس (DSL) و موتور تصحیح

### ۳.۱ گرامر
سند با `<!DOCTYPE html ><html><body>` شروع می‌شود و از ۲۶ برچسب ساخته می‌شود؛ در ۱۸,۲۷۲ درس هیچ برچسب یا ویژگی ناشناخته‌ای وجود ندارد. بلوک‌های اصلی: `<p>`، `<code>`، `<selection>`، `<webview>`، `<database>`، `<output>`.

### ۳.۲ استخراج متن مسطح (قلب موتور)
```kotlin
// متن مسطحی که ویرایشگر نشان می‌دهد
fun flatten(content: List<TextRun>): String =
    content.joinToString("") { run ->
        if (run.type == "break") "\n" else run.value.unescapeXml()
    }
```

### ۳.۳ تصحیح
```kotlin
// نوع ۱: پرکردن جای خالی — پاسخ درست خودِ کد است
fun checkFillTheGap(flat: String, gaps: List<IntRange>, placed: List<String>): Boolean =
    gaps.indices.all { i -> placed[i].trim() == flat.substring(gaps[i]) }

// نوع ۲: ورودی اعتبارسنجی‌شده — بازه روی خود <interaction> است
fun checkValidatedInput(flat: String, range: IntRange, typed: String): Boolean =
    normalize(typed) == normalize(flat.substring(range))

// نوع ۳: انتخاب — دقیقاً یک گزینهٔ درست
fun checkSelection(items: List<Item>, chosen: Set<String>): Boolean =
    chosen == items.filter { it.correct }.map { it.value }.toSet()
```

### ۳.۴ چرا این طراحی درست است
- **نویسنده پاسخ را دوباره نمی‌نویسد**؛ پاسخ = برش کد. تنها چیزی که دستی نوشته می‌شود «گزینه‌های انحرافی» است و در کل بسته همهٔ ۴,۹۳۹ گزینهٔ متنی `correct="false"` هستند — یعنی هیچ‌جا پاسخ درست به‌صورت داده ذخیره نشده.
- **تصحیح آفلاین و آنی** است، بدون سرور و بدون دور رفت‌وبرگشت.
- بازه‌ها با قاعدهٔ «break = \n» در ۱۷,۵۲۶ مورد از ۱۷,۵۲۶ مورد معتبرند؛ هیچ قاعدهٔ دیگری این سازگاری را تولید نمی‌کند.

### ۳.۵ درس کدنویسی (اجرای سمت سرور)
```kotlin
data class ExecuteFilesResponse(
    val hasPassed: Boolean,
    val hostedProjectUrl: String?,
    val consoleOutput: String?,
    val error: String?,
    val tests: List<ExecuteLessonTestCase>
)
data class ExecuteLessonTestCase(val hasPassed: Boolean, val description: String, val error: String?)
```
مسیر: `POST /v1/tracks/{t}/tutorials/{tu}/chapters/{c}/lessons/{l}/runFiles`. نتیجه در رابط کاربری به چهار حالت تبدیل می‌شود: `TestsPassed`، `TestsFailed`، `CompilerError`، `ConnectivityError` و به‌صورت «`n/m checks passed`» و «`Condition i`» نمایش داده می‌شود. نام داخلی سرویس اجرا از یک رشتهٔ خطا در بسته پیدا می‌شود: **MFEL**.

## ۴. پایگاه داده و همگام‌سازی

```sql
CREATE TABLE lesson_progress (
  lesson_id INTEGER NOT NULL, completed_at INTEGER NOT NULL, started_at INTEGER NOT NULL,
  tries INTEGER NOT NULL, tutorial_id INTEGER NOT NULL, tutorial_version INTEGER NOT NULL,
  track_id INTEGER NOT NULL, publish_set_version INTEGER NOT NULL,

  PRIMARY KEY(lesson_id, tutorial_id));

CREATE TABLE chapter_completions (
  chapter_id INTEGER NOT NULL, created_at INTEGER NOT NULL,
  track_id INTEGER NOT NULL, tutorial_id INTEGER NOT NULL, PRIMARY KEY(chapter_id, track_id));

CREATE TABLE tutorial_completions (
  tutorial_id INTEGER NOT NULL, is_completed INTEGER NOT NULL, updated_at INTEGER NOT NULL,
  track_id INTEGER NOT NULL, PRIMARY KEY(tutorial_id, track_id));
```

الگوی صف خروجی: نوشتن با `in_queue=1` → ارسال با WorkManager → در صورت موفقیت **حذف ردیف**. یعنی Room فقط «پیشرفتِ هنوز ارسال‌نشده» را نگه می‌دارد و تاریخچه در سرور است. شمارنده‌ها یکنوا هستند (`tries`, `attempts`, `completed_at`) و همین، نیاز به حل تعارض را حذف می‌کند.

## ۵. معماری آموزشی (Pedagogy)

### ۵.۱ چرخهٔ یادگیری در یک درس
```
مفهوم (متن) → مثال کد (غیرسنجشی) → تمرین سنجشی → بازخورد درجا
   ├─ درست: پیام تشویقی چرخشی + گاهی بلوک «توضیح عمیق‌تر» (۱۴۳ مورد در کل بسته)
   └─ غلط : ۱۳,۰۴۳ بلوک درمانی (visible-if="wrong") + راهنما → «دیدن راه‌حل» با تأیید
```

### ۵.۲ چهار سازوکار سختی (که غالباً با هم اشتباه می‌شوند)
| سازوکار | دانه‌بندی | تطبیقی؟ | شاهد |
|---|---|---|---|
| برچسب فصل `practiceLevel1..3` | فصل | خیر (نویسنده) | ۱۱,۳۷۳ / ۲,۳۶۲ / ۴,۰۹۶ درس |
| حالت سخت (`hardModeContent`) | درس | خیر (انتخاب کاربر) | ۶,۰۵۸ درس |
| حالت سریع (Fast mode) | فصل | **بله** (بر اساس سرعت) | ۲۶ رشته، «You're breezing through!» |
| تمرین هوشمند | انتخاب فصل | بله (سرور) | `SmartPractice*` |

### ۵.۳ آنچه در معماری آموزشی میمو **نیست**
- برآورد توان یادگیرنده (مدل IRT/Elo) وجود ندارد.
- مرور فاصله‌دار برنامه‌ریزی‌شده وجود ندارد؛ صف موجود، صف *همگام‌سازی* است نه تکرار.
- مهلت و وزن مبحث (دفترچهٔ آزمون) وجود ندارد.
- مدل ضعف به تفکیک مبحث وجود ندارد؛ آمار تمرین فقط «زمان» و «تعداد فصل» است.

### ۵.۴ حلقهٔ تطبیق واقعی (آنچه هست)

## ۷. ریسک‌های معماری برای تیم پیاده‌ساز

1. **نرمال‌سازی فارسی**: بدون سیاست مکتوب (ی/ك، نیم‌فاصله، ارقام، ممیز)، تصحیح آفست خطای آموزشی تولید می‌کند. این بزرگ‌ترین ریسک فنی پروژه است.
2. **محتوای درون‌اپ**: برای محتوای سالانهٔ کنکور مناسب نیست؛ باید دانلودی و امضاشده شود.
3. **سه صفحهٔ پیکربندی**: در میمو Firebase + سرویس کانفیگ + آزمایش محتوا با تقدم نامعلوم هم‌زیستی دارند؛ یک صفحه و یک قاعدهٔ تقدم مکتوب لازم است.
4. **ابزار داخلی در بیلد تولید**: میمو ۵۵ کلاس منوی توسعه‌دهنده را منتشر کرده است؛ این کار نباید تکرار شود.
5. **آزمون (حالت B) ۶۰٪ کار مهندسی محصول است** و در میمو هیچ پیشینه‌ای ندارد.

## ۸. جمع‌بندی معماری

قوت اصلی میمو در **کوچکی زبان درس و مشتق‌شدن پاسخ از محتوا** است: با ۲۶ برچسب و سه مقدار `visible-if` می‌توان ۱۸ هزار درس را سرو کرد، آفلاین تصحیح کرد و بدون ذخیرهٔ کلید پاسخ از تقلب محتوایی جلوگیری کرد. ضعف اصلی، **نبود مدل یادگیرنده و مهلت** است. معماری مناسب کنکور = معماری میمو در لایهٔ محتوا و تصحیح + یک لایهٔ تازه در سطح «سؤال و مابه‌ازای زمانی».
