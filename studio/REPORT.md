# گزارش جامع — از `render_film.py` تا خط تولید زنجیره‌ای

> این سند «حافظهٔ پروژه» است: هر چه سنجیده شد، هر جا شکست خورد، و چرا.
> تا زمانی که این فایل در ریپو هست، هیچ‌کدام از این‌ها دوباره گم نمی‌شود.
> آخرین بازبینی: ۲۰۲۶-۱۰-۳۰

---

## ۰) خلاصهٔ یک‌پاراگرافی

دو گردش کار ساختیم و دومی اولی را رد کرد. گردش کار اول («۳۷ شات، هر کدام ۴.۰۳
ثانیه، مونتاژ با xfade») فیلمی ساخت که کاربر رد کرد: صدا سینک نبود، شات‌ها به هم
نمی‌خوردند، خط دیالوگ با کاراکتر روی تصویر جور نبود، کارگردانی ضعیف بود. علت را
اندازه گرفتیم: **۸ خط از ۱۷ خط از روی برش رد می‌شد**، و **کلیپ‌ها تا پایان ۴ ثانیه
۶۶٪ از هویت خودشان فاصله می‌گرفتند**. گردش کار دوم («صدا اول، بهترین‌از‌چند، داور
عینی، پل فریم») این دو را از ریشه هدف می‌گیرد و سرعت مونتاژ را از چند دقیقه به
**۲۰ ثانیه برای ۱۶ ثانیه فیلم** رساند.

## ۱) گردش کار اول — چه بود، چه شد

```
screenplay ─► still (Mivi stitchImage) ─► clip 4.03s (Mivi beatImage2Video)
           ─► 37 شات ─► assemble (xfade) ─► srt ─► PNG overlay ─► mix ─► loud ─► qc
```

فایل‌ها: `studio/filmkit.py` (verbs `new/plan/still/shot/chain/assemble/mix/srt/vo/qc/frames/deliver`)،
`studio/render_film.py` (رانر CI با بودجهٔ زمانی و حالت resumable).

### ایرادهای واقعی — با عدد، نه با حس

| ایراد کاربر | ریشهٔ فنی | مدرک |
|---|---|---|
| «صدا سینک نبود» | تایم‌لاین از تخمین ۴.۰۳s ساخته می‌شد، نه از طول واقعی صدا | `sync` گفت ۸ خط از ۱۷ خط از روی برش رد می‌شوند (s7 4.4s، s23 4.4s، s28 6.3s) |
| «شات‌ها درست نبودند» | ۲۶ پلان از ۳۷ پلان فقط **کراپ** یک عکس بود؛ دوربین واقعی وجود نداشت | `assets/` هفت مستر دارد، اما ۳۷ شات |
| «خط با کاراکتر جور نبود» | پوشش یک‌نفره روی پلیت‌های بی‌گوینده؛ گوینده لزوماً روی تصویر نبود | `speaker_picture_mismatch` (این یکی صفر بود، ولی پوشش تصویری مشکل داشت) |
| لب‌سینک | Mivi اصلاً audio-driven نیست | `mivi_web/README.md` — قفل حساب با `1001 invalid user` |
| رانش لباس | هیچ قفل کاراکتری نبود | `scorer.py`: فریم آخر s28 در برابر استیل مرجع = **۰.۳۴** |
| کارگردانی ضعیف | همهٔ شات‌ها یک اندازه، بدون پیشروی نما | بازبینی شات‌لیست |

### عدد شاخص: ۸۵ ثانیه انکود برای ۳۷ کلیپ، و ۴ تا ۶ دقیقه برای مسیر xfade

## ۲) گردش کار دوم — خط تولید فعلی

```
خط دیالوگ ─► TTS ─► طول واقعی هر خط ─┐
                                     ├─► تایم‌لاین (طول شات = طول خط)
stills (CHAR_LOCK) ─► N کاندید استیل ┤
                                     ├─► scorer.pick ─► برنده
N کاندید کلیپ ───────────────────────┘
                                     │
        chainkit.bridge (پل فریم: آخرین فریم → ورودی لینک بعد)
                                     │
        cutlist.build (سگمنت → concat -c copy → VO mix → libass → loudnorm)
                                     │
                              scorer + qc  ─► تحویل
```

| ابزار | کار | وضعیت |
|---|---|---|
| `studio/scorer.py` | داور عینی بهترین‌از‌چند (۸ متریک، CPU) | ✅ تست‌شده روی ۱۳ کاندید واقعی |
| `studio/chainkit.py` | پل فریم + راهنما (edge/gray/annot) + audit رانش | ✅ تست‌شده |
| `studio/cutlist.py` | مونتاژ audio-first از تایم‌لاین JSON | ✅ ۱۶ ثانیه در ۲۰.۸ ثانیه |
| `studio/mivi_shot.py` | تولید Mivi از داخل GitHub Runner | ✅ (پل خروجی شبکه) |
| `studio/filmkit.py` | زیرساخت فیلم بلند (vo/sync/srt/assemble/loud/qc) | ✅ |

## ۳) یافته‌های مهندسی معکوس Mivi

| یافته | مدرک |
|---|---|
| موتور = **Wan + LoRA** | نام فایل سمت سرور: `img2video_wanlora_tail-….mp4` |
| طول ثابت **۴.۰۳ ثانیه** | همهٔ خروجی‌ها، مستقل از کیفیت |
| کیفیت = `quality: 1\|2` | q=1 → ۶۰۸×۴۱۶، q=2 → ۱۲۸۰×۹۶۰ |
| **۳۲ فریم/ثانیه** | خانوادهٔ Wan معمولاً ۱۶ یا ۲۴ می‌دهد ⇒ خط لولهٔ اختصاصی پلتفرم |
| بدون seed، بدون تصویر مرجع، بدون فریم آخر | نه در API، نه در dex |
| لب‌سینک قفل است | `1001 invalid user` روی اندپوینت صدا |
| خروجی اپ از خروجی beat ما تمیزتر است | مقایسهٔ بیت‌ریت و نویز، `mivi_web/README.md` |

پیامد طراحی: **هر شاتی که Mivi می‌سازد، در پایان خودش یک کاراکتر دیگر است.**
پس یا باید بعد از هر ۲ پرش re-anchor کرد، یا باید FLF داشت (که Mivi ندارد).

## ۴) مشکل اینترنت — دقیقاً چه بود و چطور حل شد

### مشکل
سندباکس ایجنت فقط به چند دامنه دسترسی دارد. نتیجه:

```
curl https://cpi.ufotosoft.com          → 000 در ۰.۰۶ ثانیه
curl https://algo-v1.wiseoel.com        → 000 در ۰.۰۶ ثانیه
```

`000` در ۶۰ میلی‌ثانیه یعنی مسدودسازی در پروکسی خروجی، نه خطای سرور. پس
**تولید زنده از داخل سندباکس ممکن نبود** — و همین باعث شد کلیپ ۱۶ ثانیه‌ای اول از
فوتیج موجود بریده شود.

### راه‌حل: GitHub Actions به‌عنوان پل خروجی
رانرهای گیت‌هاب اینترنت عادی دارند. پس تولید را از سندباکس به رانر منتقل کردیم:

```
سندباکس ──push .mivi-trigger──► GitHub Actions (mivi.yml)
                                      │  internet: ✓
                                      ▼
                              Mivi: upload → create → poll → download
                                      │
                                      ▼
                        commit: films/short16/clips_gen/*.mp4 + gen_report.json
                                      │
سندباکس ◄──── git pull ──────────────┘
```

فایل‌ها:
- `.github/workflows/mivi.yml` — تریگر روی تغییر `.mivi-trigger` (چون `gh workflow run` از این حساب ۴۰۳ می‌دهد)
- `studio/mivi_shot.py` — درایور تولید، فقط stdlib، هر تلاش را جدا نگه می‌دارد (`g1_a1.mp4`, `g1_a2.mp4`)
- `films/short16/gen_jobs.json` — شرح کار: استیل + پرامپت + تعداد تلاش

نکتهٔ مهم: چون تولید رایگان است، هر شات **۲ تلاش** می‌گیرد و هر دو نگه داشته
می‌شوند؛ انتخاب بعد از تولید انجام می‌شود، نه با حدس قبل از آن.

### نتیجهٔ عملی — اجرا شد و کار کرد (۲۰۲۶-۱۰-۳۰)

| مورد | نتیجه |
|---|---|
| ران `mivi` | ✅ موفق، `14m22s` |
| کلیپ تولیدشده | ۸ فایل، ۴ شات × ۲ تلاش، همه سالم |
| زمان هر کلیپ | **۱۰۵ تا ۱۴۶ ثانیه** (میانگین ۱۰۸) |
| بازگشت به ریپو | کامیت خودکار `mivi: 06:05 generation batch` |
| گزارش | `films/short16/clips_gen/gen_report.json` |

یعنی تولید از سندباکس **کاملاً شدنی است** — فقط از راه رانر، نه از راه پروکسی.

### محدودیت‌های این راه‌حل (باید بدانی)
- تأخیر: هر بار push → صف رانر → تولید → commit. برای یک دستهٔ ۴ شاتی چند دقیقه.
- لاگ رانر از سندباکس خوانده نمی‌شود (لاگ روی `objects.githubusercontent.com` است که مسدود است)؛ مدارک از راه **کامیت خود رانر** برمی‌گردد، نه از لاگ.
- سقف کامیت ۵۰ مگابایت است؛ کلیپ ۴ ثانیه‌ای ۷۲۰p چند مگابایت است، پس مشکلی نیست. فیلم کامل باید artifact یا Drive باشد.

## ۷) ریسک‌ها و کارهای باقی‌مانده

1. **لب‌سینک** — با Mivi ممکن نیست. یا باید پذیرفت (زیرنویس + نمای غیرگویا)، یا سرور GPU (۱۲GB کافی است: MultiTalk 480p/10s).
2. **پل فریم واقعی (FLF)** — Mivi ندارد. تقریب فعلی: آخرین فریم → ورودی بعد، با re-anchor هر ۲ پرش.
3. **قفل کاراکتر** — `stitchImage` دو‌عکسی تنها ابزار تصویری این حساب است؛ کیفیت قفل به آن وابسته است.
4. **داور بینایی** — `scorer.py` عینی و سریع است ولی معنایی نیست (نمی‌فهمد «غم» درست بازی شده یا نه). لایهٔ بعدی: بازبینی تصویری توسط خود ایجنت.
5. **`lipsync_r` پروکسی است** — برای رتبه‌بندی خوب، برای تأیید نهایی نه.

## ۸) بازتولید در ۶ دستور

```bash
# ۱ صدا
python3 studio/filmkit.py vo   films/<name> && python3 studio/filmkit.py sync films/<name>
# ۲ انتخاب شات با داور
python3 studio/scorer.py pick films/<name>/clips/*.mp4 --ref <still>.png --audio <vo>.mp3
# ۳ تولید (روی رانر)
printf '%s' "$(date -u)" > .mivi-trigger && git commit -am "gen" && git push
# ۴ راهنما و پل فریم
python3 studio/chainkit.py bridge films/<name> --from-clip <clip>.mp4 --prompt "..."
# ۵ مونتاژ
python3 studio/cutlist.py build films/<name>/timeline.json --out films/<name>/out/final.mp4
# ۶ کیفیت
python3 studio/filmkit.py qc films/<name> && python3 studio/filmkit.py loud films/<name>
```
