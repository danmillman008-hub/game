## ۲) ADRها (خلاصهٔ تصمیم‌های معماری)

| ADR | تصمیم | دلیل | جایگزینی که رد شد |
|---|---|---|---|
| ADR-01 | MVVM + جریان یک‌طرفه (UI State از ViewModel، رخداد به بالا) | تست‌پذیری، رفتار قابل پیش‌بینی در پیکربندی مجدد | MVI کامل (سربار بی‌مورد)، MVP (منسوخ) |
| ADR-02 | DI با Hilt | استاندارد، پشتیبانی رسمی، تست ساده | Koin (سبک‌تر ولی runtime)، دستی (در مقیاس دردناک) |
| ADR-03 | Room + Flow | یکپارچگی با Compose، مهاجرت تست‌پذیر | SQLDelight (برای v1 سربار)، ObjectBox (وابستگی تجاری) |
| ADR-04 | اسکن با CameraX + ML Kit Barcode | نگهداری گوگل، پشتیبانی DataMatrix/GS1، بدون کد بومی | zxing-android-embedded (قدیمی‌تر، تجربهٔ دوربین ضعیف‌تر) — **با امکان جایگزینی اگر ML Kit روی دستگاه‌های هدف ضعیف بود** |
| ADR-05 | پارسر GS1 آماده + لایهٔ تطبیق ایران | استاندارد پیچیده است؛ باگ محلی نمی‌خواهیم | پیاده‌سازی از صفر |
| ADR-06 | تک‌اپ multi-module (نه multi-repo) | سرعت بیلد، سادگی نسخه‌بندی | چند ریپو (سربار بی‌فایده در این اندازه) |
| ADR-07 | Coroutines/Flow، ممنوعیت GlobalScope | کنترل چرخهٔ عمر | RxJava (سنگین‌تر) |
| ADR-08 | خروجی اکسل با کتابخانهٔ بالغ (Apache POI در Android یا سبک‌تر) — **تحقیق در فاز ۵** | ریسک حجم/متدهای بالاست | تولید دستی xlsx (در وب‌اپ جواب داد، در اندروید شکننده است) |

### ADR-04 با جزئیات (چون ریسک دارد)
- گزینهٔ A: **ML Kit** (`com.google.mlkit:barcode-scanning`) — پشتیبانی رسمی، بدون کد بومی، حجم APK بیشتر (مدل ~۲.۲MB در باندل).
- گزینهٔ B: **zxing-cpp** (همان که `pharmascan` استفاده می‌کند) — سبک‌تر، سریع، Apache-2.0، ولی نیاز به NDK/JNI.
- **تصمیم:** A برای v1 (سرعت توسعه، بدون NDK). اگر بنچمارک روی دستگاه هدف ضعیف بود، B جایگزین می‌شود. **نقطهٔ تعویض، پشت یک اینترفیس `BarcodeScanner` است تا تغییر، بازنویسی UI را لازم نداشته باشد.**

## ۴) مدل خطا (بدون استثنای بی‌صدا)

```kotlin
sealed interface AppError {
    data class NotFound(val what: String) : AppError
    data object NeedsManualEntry : AppError
    data class Network(val retryable: Boolean, val detail: String?) : AppError
    data class Validation(val field: String, val rule: String) : AppError
    data class Storage(val detail: String) : AppError
    data class LicenseBlocked(val reason: String) : AppError
    data object Unknown : AppError
}

sealed interface Outcome<out T> {
    data class Ok<T>(val value: T) : Outcome<T>
    data class Err(val error: AppError) : Outcome<Nothing>
}
```

قواعد:
- هیچ `catch (e: Exception) {}` خالی. هر خطا یا نگاشت می‌شود یا لاگ با شناسه.
- خطاهای شبکه‌ای که برگشت‌پذیرند (timeout، 5xx) به‌طور خودکار **یک بار** با فاصلهٔ کوتاه تکرار می‌شوند، سپس به کاربر گزارش می‌شوند.
- پیام کاربر فارسی و عملی است؛ جزئیات فنی در بخش «جزئیات» یا فایل لاگ.

## ۵) مدل نخ‌بندی و اجرا

| کار | جای درست |
|---|---|
| دسترسی DB | `Dispatchers.IO` (Room خودش مدیریت می‌کند ولی DAOهای suspend) |
| پارس GS1 | `Default` (سبک است: کمتر از ۱ms) |
| رمزگشایی/امضا | `Default` |
| شبکه | OkHttp/`IO` |
| محاسبات موجودی و تجمیع | `Default`، در UseCase، نه در Composable |

ممنوع: هر کاری در `main` بجز به‌روزرسانی state. ممنوع: `GlobalScope`، `runBlocking` در مسیر UI.

## ۶) بودجهٔ عملکرد (به‌صورت عدد قابل شکست)

| سنجه | بودجه | چطور سنجیده می‌شود |
|---|---|---|
| باز شدن سرد (cold start) تا اولین فریم تعاملی | **< ۱٬۵۰۰ms** | Macrobenchmark (baseline profile) |
| اسکن → نتیجهٔ محلی روی فرم | **< ۳۰۰ms** | تست ابزاری + Trace |
| جست‌وجوی نام روی ۱۰۰٬۰۰۰ ردیف | **< ۱۵۰ms** | بنچمارک JVM روی DB واقعی |
| ثبت یک تراکنش (شامل به‌روزرسانی موجودی) | **< ۵۰ms** | بنچمارک |
| بازسازی کامل موجودی از ۱٬۰۰۰٬۰۰۰ تراکنش | **< ۳ ثانیه** | تست بار |
| مصرف RAM پایه | **< ۲۰۰MB** | Android Studio Profiler |
| اندازهٔ APK | **< ۲۵MB** | خروجی بیلد |

**قاعده:** این اعداد ادعا نیستند؛ در فاز ۶ با `Macrobenchmark` و `Benchmark` گوگل روی دستگاه واقعی اندازه‌گیری و در CI ثبت می‌شوند. هر رگرسیون بیش از ۱۰٪، بیلد را قرمز می‌کند.

## ۷) استراتژی تست

**هرم تست:**

```
        /\
       /  \      E2E (کم): ۳ سناریو — اسکن→ثبت→خروجی، بازیابی پشتیبان، لایسنس
      /────\
     /      \    تست ابزاری (متوسط): دیتابیس + مهاجرت + اسکن تصویری
    /────────\
   /          \  تست واحد (زیاد): پارس GS1، محاسبهٔ موجودی، تاریخ شمسی، اعتبارسنجی
  /────────────\
```

**اجباری‌های v1:**
1. **پارس GS1 با fixture واقعی:** حداقل ۱۵ نمونه از بارکدهای واقعی داروخانه (شامل پیشوند `]d2`، بدون FNC1، انقضای `00`، payload تکراری، بچ با `/` و `-`). هر نمونه = یک تست.
2. **تاریخ:** تبدیل شمسی↔میلادی برای همهٔ ۱۲ ماه + سال کبیسه + اول/آخر ماه.
3. **موجودی:** سناریوهای کارتن/باز/ترکیبی، بازگشت از منفی، شمارش مجدد.
4. **مهاجرت:** از نسخهٔ ۱ به N با دادهٔ نمونه، بدون از دست رفتن ردیف.
5. **ضد دوباره‌ثبت:** دو بار ارسال با یک `client_uuid` = یک تراکنش.
6. **پوشش منطق دامنه:** حداقل ۸۰٪ (JaCoCo/Kover).

**CI (GitHub Actions):** lint + تست واحد + بیلد debug + تست مهاجرت + بنچمارک سبک، روی هر PR. بیلد release فقط با تگ.

## ۹) لایهٔ استعلام (چون ریسک‌دار است، ایزوله می‌شود)

```
Domain: ProductLookup (interface)
   ├── LocalLookup      (DB)        ← همیشه اول
   ├── RemoteLookup     (TTAC)      ← اختیاری، خاموش‌شدنی
   └── CompositeLookup  (زنجیره + کش + fallback)
```

- ترتیب: محلی → کش استعلام → از راه دور → دستی.
- هر تلاش از راه دور: حداکثر ۳ درخواست، با فاصله‌گذاری و کش TTL (کد اصالت کوتاه، کاتالوگ بلند).
- اگر سرویس جواب نداد: **پیام روشن + ادامهٔ کار**، هرگز بلاک کردن کاربر.
- هیچ هدر سفارشی، هیچ کلید در اپ، هیچ درخواست انبوه.
