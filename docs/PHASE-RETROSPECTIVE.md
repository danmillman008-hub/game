# بازبینی روند کار — چرا نسخهٔ ۲.۰.۰ به درد نخورد

این سند خودانتقادی است، نه گزارش موفقیت. بر اساس بازخورد کارفرما:
«بعد از ثبت اولین دارو کرش کرد»، «نوار پایینی روی دکمه‌ها افتاده»،
«خیلی از امکانات فایل HTML نیست»، «رابط کاربری مزخرف».

## ۱. ترتیب کار اشتباه بود

| ادعا در برنامهٔ فازها | آنچه واقعاً شد |
|---|---|
| فاز A/B: اسلایس عمودی دارو/بچ/موجودی | ✅ لایهٔ داده و دامنهٔ تمیز ساخته شد (این بخش واقعاً خوب است) |
| فاز C: اتصال UI به دامنه | ⚠️ UI «ساخته شد» ولی **جریان واقعی کاربر تست نشد** |
| فاز G: تست | ❌ تست‌ها فقط لایهٔ داده را می‌دیدند؛ **یک تست هم مسیر «ثبت دارو → صفحهٔ بعد» را اجرا نمی‌کرد** |
| ادعای «۳۱ تست سبز» | این عدد درست بود، ولی **هیچ تستی اپ را باز نمی‌کرد** |

**درس:** «بیلد سبز + تست واحد سبز» تضمین «کار می‌کند» نیست. بیلد سبز بود و اپ وقتی
کاربر واقعی لمسش کرد کرش کرد.

## ۲. باگ‌ها و ریشه‌شان

| باگ | ریشهٔ واقعی | چرا زودتر گرفته نشد |
|---|---|---|
| کرش بعد از ثبت اولین دارو | هیچ لاگی از دستگاه وجود نداشت؛ مسیر «ذخیره → ناوبری → صفحهٔ جزئیات» هیچ تستی نداشت | نبود CrashReporter و نبود تست جریان |
| نوار پایین روی دکمه‌ها | `FloatingBottomBarScaffold` محتوا را در یک `Box` **زیر** نوار می‌گذاشت؛ هیچ `padding` پایین اعمال نمی‌شد | طرح «شناور» بدون محاسبهٔ ارتفاع نوار |
| نبود امکانات HTML | مدل داده از **خلاصهٔ حافظه** ساخته شد، نه از خواندن کد HTML | سند «هم‌ارزی» وجود نداشت |
| UX ضعیف | فرم ثبت ۱۱ فیلد داشت و چرخهٔ روزانه (ورود/خروج سریع) در آن گم بود | طراحی بر اساس «موجودیت» نه «کار روزانه» |

## ۳. اصلاحات ساختاری که انجام شد

1. **CrashReporter**: هر کرش با نسخه، مدل دستگاه و stack trace ذخیره می‌شود و در شروع
   بعدی به کاربر نشان داده می‌شود (کپی با یک دکمه، بدون ارسال خودکار).
2. **چیدمان**: نوار پایین حالا فضای خودش را رزرو می‌کند (`padding(bottom)`)؛ هیچ دکمه‌ای
   زیر آن نمی‌رود. `LocalBottomBarInset` هم برای صفحه‌هایی که فضای بیشتری می‌خواهند.
3. **تست جریان واقعی**: `PharmacySaveFlowTest` با Room واقعی، مسیر
   «ثبت دارو → فهرست → جزئیات → خروج» را اجرا می‌کند.
   `PharmacyScreenSmokeTest` همهٔ صفحه‌ها را با دادهٔ واقعی‌شکل رندر می‌کند.
4. **سند هم‌ارزی**: `docs/HTML-PARITY-SPEC.md` — استخراج‌شده از **کد** فایل HTML
   (۱۱۶ تابع، ۵ تب) نه از حافظه.
5. **چرخهٔ کار روزانه** جای «فرم موجودیت» را گرفت: صفحهٔ «ثبت سریع».

## ۴. قواعد جدید برای ادامهٔ کار

1. هیچ فاز UI بدون **تست جریان** (نه فقط تست واحد) تحویل نمی‌شود.
2. هر قابلیت جدید باید ردیف متناظر در `HTML-PARITY-SPEC.md` داشته باشد؛ اگر ندارد،
   نوشته شود چرا.
3. هر تغییر DI ⇒ `KoinGraphTest`؛ هر تغییر چیدمان ⇒ بررسی «زیر نوار نبودن».
4. «کاربر ابزار خط فرمان اجرا نمی‌کند» یعنی **ما** باید پیش از تحویل، مسیر واقعی را
   روی امولاتور با `app-smoke` اجرا کنیم؛ «نصب شد و باز شد» حداقل است، نه کافی.
5. گزارش پیشرفت باید با شواهد باشد: شمارهٔ run، verdict، تعداد تست — نه صفت.

## ۵. وضعیت فعلی (پس از این دور)

| موضوع | وضعیت |
|---|---|
| کرش باز شدن اپ | ✅ `VERDICT_release=APP_RUNNING` روی امولاتور |
| کرش پس از ثبت دارو | 🔎 گزارش‌گیر کرش اضافه شد + مسیر در تست بازسازی شد؛ منتظر تأیید روی گوشی |
| نوار پایین روی دکمه‌ها | ✅ رفع ساختاری |
| ثبت سریع / ضایعات / مرجوعی / شمارش کارتن و باز | ✅ پیاده شد |
| تاریخ شمسی | ✅ با تست تبدیل |
| تاریخچهٔ سراسری | ✅ |
