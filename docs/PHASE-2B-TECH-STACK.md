# فاز ۲-ب — بازبینی بنیادی انتخاب فناوری (تصمیم دوباره)

> کارفرما پرسید: «آیا کاتلین واقعاً بهترین راه است؟ روشی را پیدا کن که بعداً هم بتوانیم تغییر بدهیم، دستمان باز باشد و به باگ‌های عجیب نخوریم.»
> این سند پاسخ همان سؤال است. **هیچ کدی نوشته نشده.** فقط شواهد، مصالحه‌ها و یک پیشنهاد.

## ۲) گزینه‌های واقعی و شواهد

### گزینهٔ A — Kotlin + Jetpack Compose (بومی)
| موضوع | شاهد |
|---|---|
| سرعت | Cold start حدود **۱۵٪ سریع‌تر**، حافظه حدود **۲۰٪ کمتر** از Flutter؛ APK پایه ~۳٫۵MB در برابر ~۱۱MB |
| دیتابیس | Room/SQLite، بهترین ابزار مهاجرت و تست در اکوسیستم |
| مقاومت | بدنهٔ Kotlin به بایت‌کد Dalvik کامپایل می‌شود و **jadx آن را تقریباً به جاوای خوانا برمی‌گرداند**؛ R8 فقط نام‌ها را تغییر می‌دهد. یعنی **منطق اپ برای مهاجم قابل خواندن است** (مگر اینکه بخش حساس را به C++/NDK ببری) |
| UI | قوی و بومی، ولی هر تغییر ظاهری نیاز به بیلد دارد؛ چرخهٔ تکرار کندتر |

### گزینهٔ B — Flutter
| موضوع | شاهد |
|---|---|
| سرعت | AOT به کد ماشین؛ ۶۰fps پایدار در لیست‌های ۱۰هزار آیتم (گاهی ۵۸–۶۰)؛ رندر یکسان روی همهٔ دستگاه‌ها (طراحی دقیق = همان چیزی که می‌بینی) |
| دیتابیس | `drift` / `sqflite`: همان SQLite، با WAL، ایندکس و FTS4/5 — برای ۱ میلیون ردیف کافی است |
| مقاومت | کد Dart به `libapp.so` (کد ماشین ARM64) کامپایل می‌شود؛ **بایت‌کد قابل دیکامپایل مثل jadx وجود ندارد**. منابع مستقل: «سخت‌تر از بایت‌کد جاوا برای مهندسی معکوس»؛ ابزارهای `blutter`/`reFlutter` هستند ولی «هزینهٔ حمله» را بالا می‌برند |
| محدودیت امنیتی (صادقانه) | `--obfuscate` فقط نام‌ها را عوض می‌کند؛ **رشته‌ها در object pool خوانا می‌مانند** (آدرس‌ها، پیام‌ها) — پس هیچ راز ثابتی در اپ نمی‌گذاریم |
| UI | چرخهٔ سریع، ویجت‌محور، RTL و فارسی کامل؛ هات‌ریلود برای تکرار طراحی |
| هزینه | APK حدود ۵–۱۵MB بزرگ‌تر؛ cold start ۳۰–۴۰٪ کندتر از بومی |

### گزینهٔ C — React Native / Expo
- مزیت: تکرار UI سریع، اکوسیستم بزرگ.
- **رد می‌شود**: باندل Hermes/JS به‌راحتی استخراج می‌شود؛ برای شرط «کرک نشود» بدترین گزینه. ریسک باگ‌های پل بومی در اسکن دوربین هم بالاتر است.

### گزینهٔ D — نگه‌داشتن وب (Capacitor) و استفاده از همان کد امروز
- مزیت: کد اثبات‌شده آماده است؛ سریع‌ترین مسیر.
- **رد می‌شود**: JS خوانا است (حتی minify‌شده)، دیتابیس سنگین در WebView کندتر، و ظاهر «اپ واقعی» با انیمیشن بومی سخت‌تر درمی‌آید. مناسب نمونهٔ اولیه است، نه محصول فروشی.

### گزینهٔ E — Kotlin Multiplatform (منطق مشترک + UI بومی)
- تمام مزایا/معایب گزینهٔ A را دارد، به‌علاوهٔ سربار concepts. برای «فقط اندروید امروز» پیچیدگی بی‌دلیل است.

## ۴) پیشنهاد من (به‌همراه ریسک‌هایش)

### Flutter به‌عنوان لایهٔ UI + منطق، و یک «هستهٔ امنیتیِ بومی» کوچک در Kotlin

```
┌──────────────────────────────────────────────┐
│  Flutter (Dart)                              │
│  UI · جریان‌ها · منطق دامنه · دیتابیس (drift) │
└───────────────┬──────────────────────────────┘
                │ Platform Channel (سطح تماس باریک، ۴ تابع)
┌───────────────▼──────────────────────────────┐
│  Android native module (Kotlin)              │
│  ۱) اثر انگشت دستگاه   ۲) بررسی امضای APK     │
│  ۳) تأیید امضای لایسنس  ۴) ساعت قابل‌اعتماد     │
└──────────────────────────────────────────────┘
```

**چرا این ترکیب؟**
- **UI سنگین و شرکتی** با Flutter سریع‌تر و قابل‌پیش‌بینی‌تر ساخته می‌شود (C1) — همان چیزی که خودت گفتی وقتش را داریم.
- **کرک**: کد اصلی در Dart AOT است (بدون دیکامپایل خوانا)، و منطق حساس لایسنس در Kotlin می‌ماند تا ابزارهایی مثل reFlutter نتوانند فقط با پچ کردن Dart، لایسنس را دور بزنند (C4).
- **دیتابیس**: SQLite خالص با WAL + ایندکس + FTS؛ همان چیزی که در فاز ۱ طراحی شد و به زبان اپ وابسته نیست (C3).
- **تغییرپذیری**: منطق در لایهٔ مستقل، UI فقط نمایش؛ پس تغییر ظاهر = تغییر ویجت، بدون دست زدن به مغز برنامه (C2).
- **آینده**: همان کد روی iOS/ویندوز/تبلت می‌رود؛ برای شرکتی که می‌خواهد نسخه‌های بعدی بفروشد، این یعنی بازنویسی صفر (C7).

**چه چیزی را از دست می‌دهیم (صادقانه):**

| از دست می‌دهیم | اندازهٔ واقعی | جبران |
|---|---|---|
| ~۱۵٪ سرعت استارت | با splash کوتاه و lazy init، برای کاربر نامحسوس | baseline profile + کم‌کردن وابستگی‌های شروع |
| ~۱۰MB حجم APK | اهمیت عملی کم | حذف assetهای اضافه، split per ABI |
| بومی نبودن ویجت‌ها | ظاهر دقیقاً همان می‌شود که طراحی می‌کنیم (برای «ظاهر شرکتی» یک مزیت است) | سیستم طراحی اختصاصی |
| دسترسی مستقیم به APIهای اندروید | با پلاگین/کانال | فقط ۴ نقطهٔ باریک که خودمان نوشتیم |

**ریسک اصلی:** وابستگی به پلاگین دوربین (`mobile_scanner`/`camera`). کاهش ریسک: پشت یک اینترفیس `BarcodeScanner`، با یک پیاده‌سازی جایگزین از پیش بررسی‌شده؛ اگر روزی مشکل شد، فقط همان ماژول عوض می‌شود.

## ۵) چطور «دستمان باز» بماند (قواعدی که از امروز اعمال می‌شوند)

1. **هیچ منطقی در UI نیست.** هر محاسبه در لایهٔ دامنه؛ UI فقط «نمایش» و «فراخوانی».
2. **قرارداد داده بین لایه‌ها ثابت و تست‌شده است** — پس می‌شود UI را کامل عوض کرد بدون اینکه مغز برنامه بلرزد.
3. **هیچ چیز به Flutter چسبیده نیست** به‌جز لایهٔ نمایش: دیتابیس SQLite استاندارد، فرمت پشتیبان JSON، خروجی اکسل استاندارد. اگر فردا خواستی به بومی یا وب برگردی، داده و قواعد همراهت می‌آید.
4. **هر ماژول یک مرز مشخص** دارد؛ تغییر در «اسکن» نباید فایل‌های «موجودی» را لمس کند.
5. **بدون state سراسری.** هر صفحه state خودش را دارد؛ این تنها راه جلوگیری از باگ‌های «چرا این عدد عوض شد».
6. **تست برای هر قاعده**؛ اگر تغییری تستی را قرمز کرد، تصمیم غلط است، نه تست.

## ۶) اگر مخالفی — گزینهٔ جایگزین آماده است

اگر بگویی «بومی می‌خواهم»، همان معماری فاز ۱ و ۲ **بدون تغییر** روی Kotlin/Compose پیاده می‌شود (دیتابیس، قواعد، مدل خطا، لایسنس همه مستقل از زبان طراحی شده‌اند). تنها چیزی که عوض می‌شود لایهٔ نمایش است. یعنی تصمیم امروز، در را نمی‌بندد.

3. با ۶ قاعدهٔ بخش ۵ (مخصوصاً «هیچ منطقی در UI») موافقی؟

## ۸) پاسخ صادقانه به «کرک نشود» — هیچ گزینه‌ای ضدکرک نیست

این بخش تلخ است ولی باید قبل از تصمیم خوانده شود.

| ادعا | واقعیت |
|---|---|
| «اگر کاتلین باشد کرک نمی‌شود» | غلط. `jadx` بایت‌کد Dalvik را تقریباً به جاوای خوانا برمی‌گرداند؛ حتی بدون سورس، منطق لایسنس قابل خواندن است. R8 فقط نام‌ها را کوتاه می‌کند. |
| «اگر Flutter باشد کرک نمی‌شود» | غلط. `blutter` و `reFlutter` برای دیکامپایل و پچ کردن `libapp.so` وجود دارند و فعال نگه داشته می‌شوند. |
| «`--obfuscate` امنیت می‌آورد» | ناقص. فقط نام‌ها را عوض می‌کند؛ **رشته‌ها در object pool خوانا می‌مانند**. |
| «چک آفلاین در اپ کافی است» | نه. هر بررسی‌ای که کاملاً داخل اپ باشد، با `frida` یا پچ یک `if` قابل دور زدن است. |

**پس چه چیزی واقعاً کار می‌کند؟** فقط بالا بردن هزینهٔ حمله، در چهار لایه:

1. **امضای دیجیتال لایسنس با Ed25519.** کلید عمومی در اپ، کلید خصوصی هرگز در اپ نیست. کاربر نمی‌تواند لایسنس جعل کند، فقط می‌تواند «دور بزند».
2. **اتصال لایسنس به سخت‌افزار.** اثر انگشت دستگاه (ANDROID_ID + مدل + امضای APK + شناسهٔ نصب تصادفی) در پیام لایسنس امضا می‌شود. کپی APK روی دستگاه دیگر = لایسنس بی‌اعتبار.
3. **منطق حساس در لایهٔ بومی + پخش‌شده.** بررسی نه در یک `if` بلکه در چند نقطه، با نتیجه‌ای که به محاسبهٔ موجودی/گزارش گره خورده. پچ کردن یک نقطه، اپ را به حالت خراب می‌برد (نه حالت آزاد).
4. **لایسنس کوتاه‌مدت + بازهٔ آفلاین ۳۶۵ روز.** هر سال تمدید. اگر کسی نسخهٔ کرک‌شده بسازد، فقط یک سال از آن استفاده می‌کند — و نسخه‌های بعدی امضای جدید می‌خواهند.

**آنچه نمی‌کنیم (تئاتر امنیتی):** مبهم‌سازی دستی، بررسی امضای APK به‌تنهایی، «ضد دیباگ» ساده، مخفی‌کردن رشته‌ها در فایل. اینها فقط یک روز وقت مهاجم را می‌گیرند و نگهداری را خراب می‌کنند.

**نتیجهٔ عملی:** هدف واقع‌بینانه این است که «کرک کردن ارزان‌تر از خریدن نباشد» برای مشتری معمولی داروخانه. یک تیم حرفه‌ای با وقت کافی همیشه می‌تواند. کسی که این را چیز دیگری بگوید، چیزی می‌فروشد.
