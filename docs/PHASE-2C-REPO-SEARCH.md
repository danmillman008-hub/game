# فاز ۲-ج — جست‌وجوی مخزن آماده: آیا روی یک پروژهٔ موجود سوار شویم؟

> سؤال کارفرما: «اگر همان پروژه‌ای که در کاتلین/فلاتر نوشته شده را هستهٔ کار بگیریم و چند چیز ساده اضافه کنیم، موفقیت‌مان خیلی بالاتر نمی‌رود؟ و اگر روی اینترنت (چینی، فرانسوی، آلمانی…) چیزی هست که بیشترین تطبیق را دارد، همان را برداریم.»
> این سند نتیجهٔ جست‌وجوی واقعی است (۱۱ دسته جست‌وجو، ۶ زبان، ۲۲ کوئری روی GitHub + بررسی دقیق ۶ مخزن). تاریخ: ۲۰۲۶-۱۰-۲۴.

## ۰) خلاصهٔ یک‌خطی

**بله، سوار شدن روی یک مخزن آماده موفقیت را بالا می‌برد — ولی فقط روی «اسکلت» (۴۵–۵۵٪ کد)، نه روی «مغز» (هستهٔ دارویی، لایسنس، تیتک). هیچ مخزنی در دنیا مغز ما را ندارد.**
و یک نتیجهٔ غیرمنتظره: بهترین گزینهٔ موجود، **کاتلین** است — یعنی این جست‌وجو توصیهٔ قبلی من (فلاتر) را عوض می‌کند. دلیلش در بخش ۵.

### سه تلهٔ حقوقی که باید بشناسی
1. **«بدون مجوز» = هیچ حقی نداری.** مخزن عمومی بودن یعنی «می‌توانی بخوانی»، نه «می‌توانی در محصول تجاری بگذاری». `duekasir` (۴۳★) از این دست است — فقط برای الهام ساختاری.
2. **GPL/AGPL = محصول شما هم باید متن‌باز شود.** `codelv/inventory` و `EverShelf` (AGPL) با مدل فروش لایسنس شما **ناسازگارند**.
3. **Apache-2.0 و MIT = مجاز برای محصول بسته.** شرط: نگه‌داشتن فایل LICENSE، ذکر «تغییر داده شده»، و در Apache ثبت تغییرات. **هیچ‌کدام اجازهٔ استفاده از نام/لوگو/برند原作者 را نمی‌دهد.**

## ۳) کاندید شمارهٔ ۱ — Algidy (کاتلین، Apache-2.0)

یک اپ واقعیِ منتشرشده (سه نسخهٔ release، fastlane، CI برای ساخت) — نه پروژهٔ آموزشی.

| مشخصه | مقدار |
|---|---|
| کد | ۳۴۵ فایل Kotlin، معماری چندماژولی |
| UI | Jetpack Compose ۱۰۰٪، Material 3 |
| دی‌آی | Koin 4 (+ WorkManager integration) |
| دیتابیس | Room 2.7.2 |
| دوربین/بارکد | CameraX + ML Kit Barcode |
| پس‌زمینه | WorkManager (یادآور انقضا)، DataStore |
| تست | تست واحد واقعی برای use-caseها، ریپازیتوری‌ها، ولیدیتورها + `MainDispatcherRule` |
| ساخت | `build-logic` با convention plugin (استاندارد حرفه‌ای) |

**نقشهٔ ماژول‌ها:**
```
core/  common  data  database  datastore  designsystem  domain  model  network  notifications  presentation
feature/  inventory   scanner   food-entry   settings   analytics
app/      ناوبری، تم، نقطهٔ شروع
```

**چرا این «اسکلت» است، نه «اپ غذا»:** اسم پوشه‌ها را بردار — `inventory`، `scanner`، `notifications`، `database`، `designsystem`. هیچ‌کدام دربارهٔ غذا نیستند. دربارهٔ «قلم موجودی + بارکد + انقضا + آفلاین» هستند. یعنی همان کاری که ما می‌خواهیم، منهای کلمهٔ «دارو».

### چه چیزی را از آن می‌گیریم (و چقدر)

| بخش | میزان استفاده | کار لازم |
|---|---|---|
| `build-logic` (convention plugins) | ۱۰۰٪ | تغییر نام پکیج/امضا |
| `core/designsystem` (تم، تایپوگرافی، کامپوننت پایه) | ۷۵٪ | ری‌برند + RTL + فونت فارسی |
| `core/database` (راه‌اندازی Room، converter، DI) | ۸۵٪ | جایگزینی schema |
| `core/datastore` (تنظیمات) | ۹۰٪ | افزودن کلیدهای ما |
| `core/notifications` (WorkManager + انقضا) | ۸۵٪ | منطق «۳۰/۶۰/۹۰ روز» ما |
| `core/model` (Result/خطا/ولیدیتور) | ۶۰٪ | افزودن قواعد دارویی |
| `feature/scanner` (CameraX، مجوز، چراغ، ML Kit) | ۸۰٪ | تعویض به ML Kit باندل‌شده + پارسر GS1 |
| `feature/inventory` (جست‌وجو، فیلتر، مرتب‌سازی) | ۴۵٪ | UI کامل بازنویسی |
| `feature/analytics` | ۲۰٪ | اختیاری |
| تست‌ها و ابزار تست | ۱۰۰٪ | — |
| **دامنه (Food → Drug/Batch)** | **۱۰٪** | **بازنویسی** |

جمع تخمینی: **~۴۵–۵۵٪ از کد نهایی ما از این‌جا می‌آید** (صرفه‌جویی واقع‌بینانه: ۳ تا ۵ هفته کار معماری + باگ‌های زیرساختی که دیگر مرتکب نمی‌شویم).

## ۴) کاندید شمارهٔ ۲ — flutter_pos (فلاتر، MIT)

کیفیت خوب، معماری تمیز (Riverpod، go_router، sqflite، Clean Architecture)، ۲۱۸ ستاره و ۹۰ فورک، چندسکویی.

**اما سه مشکل جدی برای ما:**
1. **Firebase در تار و پود لایهٔ داده بافته شده** (auth، firestore، crashlytics، storage، sync queue). ما **حساب آنلاین نمی‌خواهیم**. کندن Firebase از این لایه = جراحی روی همان چیزی که باید بیشترین اطمینان را به آن داشته باشیم.
2. دامنه‌اش **فروش** است (سبد، فاکتور، چاپگر حرارتی) — نه موجودی بچ‌محور. از دامنه‌اش صفر استفاده می‌کنیم.
3. بارکد ندارد.

نتیجه: از آن ۲۵–۳۰٪ قابل استفاده است و آن ۳۰٪ هم دقیقاً همان بخشی است که به Firebase چسبیده. نسبت «سود به دردسر» پایین.

## ۵) توصیهٔ نهایی — و چرا توصیهٔ قبلی‌ام را عوض می‌کنم

در سند قبلی، فلاتر را ترجیح دادم چون فرض کردم **هر دو از صفر شروع می‌کنند** و بزرگ‌ترین مزیت فلاتر «سرعت ساخت UI» بود. آن فرض با این جست‌وجو باطل می‌شود:

| فرض قبلی | واقعیت جدید |
|---|---|
| اسکلت کاتلین را باید ۳–۴ هفته بسازیم | آماده است، Apache-2.0، با تست و CI |
| UI در فلاتر سریع‌تر است | مزیت باقی است، ولی ۳ هفتهٔ صرفه‌جویی اسکلت آن را جبران می‌کند |
| هستهٔ امنیتی باید در کاتلین باشد (کانال بین‌زبانی) | اگر کل اپ کاتلین باشد، **کانال حذف می‌شود** = یک منبع باگ کمتر |
| ریسک: تحمل دیتابیس سنگین | Room + multi-module، همان چیزی که در فاز ۱ طراحی کردیم |

### توصیهٔ به‌روزشده

> **کاتلین + Jetpack Compose، با Algidy به‌عنوان نقطهٔ شروع (fork با حفظ تاریخچه و مجوز).**
> لایه‌های زیرساخت از آن می‌آید؛ «مغز دارویی» را خودمان می‌نویسیم.

اگر فلاتر را ترجیح می‌دهی، تصمیم امروز در را نمی‌بندد: معماری فاز ۱ و ۲ (دیتابیس، قواعد، خطا، لایسنس) مستقل از زبان نوشته شده و روی فلاتر هم پیاده می‌شود — فقط ۳–۴ هفته بیشتر و یک لایهٔ کانال اضافه.

## ۶) آنچه **هیچ** مخزنی ندارد و باید خودمان بنویسیم (خندق ما)

1. موجودی **بچ‌محور** با FEFO (اولین انقضا، اولین خروج).
2. **تقویم شمسی** و نمایش تاریخ انقضای ایرانی.
3. **پارسر GS1** (GTIN + بچ + انقضا در یک رشته).
4. **استعلام تیتک** (ناشناس، بی‌صدا، با fallback).
5. **لایسنس امضاشده** (Ed25519) + اثر انگشت دستگاه + بازهٔ ۳۶۵ روز.
6. ورود/خروجی اکسل و پشتیبان، با اعداد فارسی.
7. UI چهارصفحه‌ای فارسی/RTL مطابق سند `UI-AUDIT.md`.

این‌ها همان چیزی است که محصول را «محصول» می‌کند؛ هیچ‌کدام را نمی‌شود از GitHub برداشت.

## ۷) 🚨 یافتهٔ فنی مهم: بارکد بدون سرویس گوگل

Algidy از `play-services-mlkit-barcode-scanning` استفاده می‌کند. این نسخه **به Google Play Services وابسته است**. در ایران بسیاری از گوشی‌ها (خصوصاً چینی‌های بدون GMS) سرویس گوگل ندارند و اسکنر **بالا نمی‌آید**.

**راه‌حل اجباری:** استفاده از نسخهٔ **باندل‌شدهٔ** ML Kit (`com.google.mlkit:barcode-scanning` — مدل داخل APK، بدون GMS، ~۳MB بزرگ‌تر) یا ZXing. این را از روز اول باید عوض کنیم، وگرنه اپ روی بخشی از گوشی‌های مشتری کار نمی‌کند.

## ۹) لیست تأیید

1. **کاتلین + Compose** با شروع از Algidy — قبول است؟ (این تغییر نسبت به سند قبلی است)
2. اگر فلاتر را ترجیح می‌دهی، بگو تا سند جایگزین را بنویسم (هزینه: ~۳–۴ هفته بیشتر + لایهٔ کانال).
3. اجازه می‌دهی مخزن Algidy را (`v2.0.0`) در یک شاخهٔ آزمایشی fork کنم، بیلد بگیرم و **گزارش وضعیت واقعی ساخت** بدهم قبل از هر تصمیم نهایی؟
4. تأیید می‌کنی که «مغز دارویی» (بخش ۶) را خودمان می‌نویسیم و انتظار نداریم در مخزن دیگران باشد؟
