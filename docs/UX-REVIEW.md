# بازبینی تجربهٔ کاربری — از دید یک داروساز پشت پیشخوان

این سند سه سؤال را جواب می‌دهد: کاربر روی گوشی چه می‌بیند؟ کجا گیر می‌کند؟
چه چیزی از نسخهٔ HTML «راحت‌تر» یا «سخت‌تر» شده است؟

## ۱. باگ‌هایی که واقعاً کاربر را زمین می‌زدند

| مشکل | ریشه | وضعیت |
|---|---|---|
| نوار پایین روی دکمه‌ها می‌افتد و «ثبت دارو» کلیک نمی‌شود | ارتفاع نوار ثابت ۹۶dp فرض شده بود، ولی ارتفاع واقعی = محتوا + حاشیه + نوار ناوبری سیستم؛ با فونت بزرگ بیشتر هم می‌شد | ✅ ارتفاع واقعی اندازه‌گیری و از محتوا کنار گذاشته می‌شود |
| دکمهٔ ذخیره زیر کیبورد می‌ماند | `enableEdgeToEdge` + بدون `imePadding` | ✅ `imePadding` سراسری |
| پس از ثبت اولین دارو اپ بسته می‌شود | علت قطعی در دست نبود (هیچ لاگی نبود) | 🔎 `CrashReporter` + `Breadcrumbs` فعال شد و تست خودکار دستگاه (`tools/ui-flow-test.py`) همان مسیر را اجرا می‌کند |
| تب‌های نوار پایین روی هم انبار می‌شدند (بازگشت عجیب) | `backStack.add` بدون جای‌گذاری | ✅ جای‌گذاری می‌شوند |

## ۲. آنچه از HTML «راحت‌تر» بود و باید برمی‌گشت

- **همه‌چیز در یک صفحه**: HTML یک صفحهٔ «اسکن و ثبت» داشت: کد → دارو → عملیات →
  مقدار → ثبت. اپ ما «افزودن دارو» و «جزئیات دارو» را جدا کرده بود؛ برای ثبت روزانه
  دو-سه ناوبری لازم بود. اکنون **ثبت سریع** یک صفحه است (انتخاب دارو → عملیات →
  مقدار → بچ → ثبت).
- **سه روش شمارش** با پیش‌نمایش «= ۴۰ عدد (۲ بسته)»: همان چیزی که سر قفسه لازم است.
- **استعلام خودکار تیتک** وقتی کد در انبار نیست (HTML: بی‌صدا و خودکار). حالا با یک
  سوئیچ روشن/خاموش، ماندگار بین اجراها.

## ۳. بی‌نظمی‌های ساختاری که کاربر حس می‌کند

1. **فهرست «داروها» و «داشبورد» هر دو فهرست نشان می‌دهند** — کاربر نمی‌داند کدام
   «انبار» است و کدام «خانه». باید یکی شود: خانه = داشبورد عملیاتی (کارهای امروز)،
   انبار = فهرست داروها با جست‌وجو.
2. **فیلدهای اضافی در فرم دستی** (نام ژنریک/قدرت/شکل دارویی) برای داروخانه داخلی
   نویز است؛ HTML فقط نام/شرکت/تعداد در بسته/GTIN/IRC داشت و همان کافی است.
3. **تنظیمات فعلی متعلق به قالب اولیه است** (تم، زبان، دربارهٔ ما، متن‌باز) و هیچ
   تنظیم داروخانه‌ای ندارد. کاربر انتظار دارد آستانهٔ کمبود، روز هشدار انقضا،
   پشتیبان‌گیری و پاک‌کردن داده را همان‌جا ببیند.
4. **نبود بازخورد بعد از ثبت**: در HTML پیام «ثبت شد» + فیلد خالی برای ثبت بعدی
   بود. در اپ باید بعد از ذخیره، فرم برای ثبت بعدی آماده شود (نه خروج اجباری).

## ۴. اصول طراحی که از این پس رعایت می‌شود

- هر عملیات روزانه حداکثر **سه لمس** از باز شدن اپ.
- هر صفحه یک کار اصلی دارد؛ دکمهٔ اصلی همیشه بزرگ و پایین‌ترین عنصر قابل دید.
- هیچ عددی بدون واحد نمایش داده نشود («۴۰» بد است، «۴۰ عدد · ۲ بسته» خوب است).
- تاریخ همیشه شمسی با ارقام فارسی؛ لاتین فقط در ورودی کد.
- پیام خطا باید بگوید **چه کار کنم**، نه فقط «خطا».
